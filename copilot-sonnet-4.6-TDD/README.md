# Maze Runner

Полностью клиентская процедурная игра-лабиринт на TypeScript + Vite + Canvas. Без бэкенда, без внешних ресурсов, без тяжёлых зависимостей.

## Быстрый старт

```bash
npm install
npm run dev        # Сервер разработки (http://localhost:5173)
npm run build      # Продакшн-сборка → dist/
npm run preview    # Предпросмотр продакшн-сборки
npm test           # Запуск юнит-тестов (55 тестов)
npm run test:watch # Режим наблюдения
```

## Управление

| Платформа | Способ | Как |
|-----------|--------|-----|
| Десктоп | Мышь | Ведите курсор к цели; игрок следует за ним |
| Десктоп | Клавиатура | WASD или стрелки |
| Мобильный | Виртуальный джойстик | Фиксирован внизу слева; тяните для перемещения |

**Переключение режима управления:** Настройки → Управление (Мышь / Клавиши)

## Режим отладки

Добавьте `?debug=1` к URL или нажмите `` ` `` (обратный апостроф) во время игры.

Показывает: FPS, сид лабиринта, размер сетки, ячейку игрока, число столкновений со стенами, время рендера.

## Архитектурные заметки

- **Двухканвасный рендеринг:** Стены рисуются один раз в `OffscreenCanvas`; каждый кадр композитит буфер + рисует игрока. Это позволяет не перерисовывать O(n²) стеновых сегментов каждый кадр.
- **Масштабирование «всё видно»:** Весь лабиринт масштабируется под размер viewport. Без камеры и прокрутки — проще код, лучше обработка поворота экрана.
- **Детерминированный ГПСЧ:** Алгоритм `mulberry32`. Сид = `userSeed XOR (level × 100003)`. Один и тот же уровень всегда порождает один и тот же лабиринт; у разных пользователей — разные лабиринты.
- **Коллизии:** Круг против осе-параллельных отрезков. Проверяются только сегменты в окрестности 3×3 ячейки (~12 сегментов максимум). Разрешение — выталкивание по нормали стены + скольжение по касательной.
- **Кривая сложности:** `gridSize = min(5 + floor((level-1) × 1.4), 38)`, `cellSize = clamp(600/gridSize, 18, 64)`, инъекции петель каждые 3 уровня.

## Ретроспектива TDD

Проект разрабатывался по методологии строгого **Test-Driven Development**: для каждого логического модуля тесты писались *до* реализации.

### Что получилось хорошо

**1. Тесты как точная спецификация.**
Написание тестов до кода заставило чётко определить контракт каждого модуля *до* появления какого-либо кода. Например, тесты генератора лабиринтов задали требования: «внешние стены всегда сплошные», «симметрия стен соблюдается между соседями», «BFS из старта достигает каждой ячейки». Именно эти свойства стали точными требованиями, которые направляли реализацию. Без TDD некоторые из них (особенно симметрия стен) были бы обнаружены как баги только во время игрового тестирования.

**2. Бесстрашный рефакторинг.**
Когда логика инъекции петель в `generator.ts` была переписана с прямого обхода на функциональный массив кандидатов, набор из 26 тестов подтвердил за 8 мс, что связность сохранена. Страховочная сетка сделала структурные изменения безопасными.

**3. Раннее обнаружение краевых случаев.**
Тест `seed 0 works without infinite loop or NaN` напрямую поймал реальный баг: исходная реализация `mulberry32` при seed=0 выдавала полностью нулевое состояние и генерировала `NaN`. Тест существовал до написания кода; исправление (отображение 0 → 1) было немедленным.

**4. Чистый дизайн модулей.**
Дисциплина «сначала напиши импорт для теста» вынуждала делать модули маленькими, сфокусированными и импортируемыми изолированно. `collision.ts` экспортирует чистые функции (`closestPointOnSegment`, `circleVsSegment`, `resolveCircleVsSegment`), которые тривиально тестируемы и компонуемы. Подход «один большой класс» сделал бы юнит-тестирование практически невозможным.

**5. Уверенность при интеграции.**
Когда дело дошло до связывания всего в `main.ts`, вся фундаментальная логика (ГПСЧ, генерация лабиринтов, математика коллизий) уже была доказана корректной 55 тестами. Отладка интеграции касалась только связующего кода, а не базовой логики.

**6. Живая документация.**
Тестовые файлы служат точной, исполняемой документацией. `maze.test.ts` — лучшая спецификация `generateMaze`, чем любой комментарий в README.

### Что оказалось сложнее / недостатки

**1. Тесты для рендеринга и stateful UI непрактичны.**
TDD прекрасно работает для чистых функций (ГПСЧ, геометрия, генерация лабиринтов). Для модулей, зависящих от DOM, Canvas API или `requestAnimationFrame`, подход становится неудобным. Рендерер (`renderer.ts`), игровой цикл (`game.ts`) и все UI-модули написаны без тестов — не потому что они неважны, а потому что их осмысленное тестирование потребовало бы headless-браузера, мок-контекстов Canvas и сложной симуляции событий. Это реальное ограничение TDD для фронтенд-разработки игр.

**2. Написание тестов для неизвестных API замедляет начальный дизайн.**
Для коллизионного движка тестовый файл пришлось переделывать дважды, пока формировались сигнатуры функций. TDD предполагает, что вы знаете API до написания тестов; в исследовательском коде само API — это неизвестная величина. Ритм «красный-зелёный-рефакторинг» ломался, когда начальные предположения об API оказывались неверными.

**3. Накладные расходы на поддержку тестов.**
После рефакторинга `solver.ts` (возвращаемый тип сменился с `Cell[]` на `Point[]`) пришлось обновить шесть утверждений в тестах. При более глубоких тестовых наборах эти расходы растут. Тесты могут замедлять итерации, если они перегружены деталями реализации, а не проверяют поведение.

**4. Соблазн написать тесты *после* и ретроактивно пройти их.**
Под давлением сроков возникает искушение сначала реализовать, а потом написать «подтверждающие» тесты. Это сводит на нет смысл TDD: тесты, написанные после реализации, проверяют *что код делает*, а не *что он должен делать*, пропуская баги, которые код уже содержит. Нужна дисциплина и инструменты (CI, контролирующий порядок коммитов).

**5. Пробелы в покрытии интеграционных путей.**
55 юнит-тестов хорошо покрывают алгоритмическое ядро, но оставляют непротестированными игровой цикл, пайплайн рендеринга и полные пользовательские сценарии. Полноценный TDD-проект включал бы также интеграционные тесты (например, end-to-end через Playwright/Puppeteer) — здесь они выходили за рамки задачи.

### Заключение и рекомендации для улучшения TDD

**TDD высокоэффективен для алгоритмического кода и преобразования данных** — а это именно ядро игрового движка (генерация лабиринтов, поиск пути, математика коллизий, ГПСЧ). Для этих модулей цикл «красный-зелёный-рефакторинг» даёт результат: меньше багов, чище API, лучше модульность.

**TDD менее эффективен (но не бесполезен) для UI, рендеринга и stateful-систем.** Здесь лучше работает гибридный подход:
1. Извлекать чистую логику из UI-компонентов (например, `formatTime`, `getLevelParams`, `recordBestTime`) и покрывать её TDD-тестами.
2. Использовать интеграционные/E2E-тесты (Playwright) для пользовательских сценариев.
3. Использовать snapshot-тесты для UI-компонентов.

**Практические рекомендации для будущих TDD-циклов:**

| Рекомендация | Зачем |
|--------------|-------|
| Писать тесты до любого кода реализации, без исключений | Предотвращает «предвзятость подтверждения» в дизайне тестов |
| Тестировать поведение, а не реализацию | Тесты переживают рефакторинг; тесно связанные с реализацией — нет |
| Держать тестовые модули маленькими и сфокусированными (один `describe` на экспортируемую функцию) | Проще поддерживать; сбои точно указывают на причину |
| Параметризовать тесты краевыми значениями | Seed=0, пустые массивы, максимальные значения — дёшево добавить, высокая ценность |
| Добавить `vitest --coverage` в CI-гейт | Предотвращает регрессию покрытия без ручной проверки |
| Писать краткий «контрактный комментарий» в начале каждого тестового файла | Документирует намерение; помогает будущим контрибьюторам |
| Агрессивно отделять чистые функции от побочных эффектов | Код с побочными эффектами (DOM, I/O, время) — враг юнит-тестирования |
| Инвестировать в минимальный E2E-набор для критических пользовательских сценариев | Дополняет юнит-тесты для интеграционных путей, недоступных модульным тестам |

**Самая ценная практика:** держать фазу написания тестов полностью отдельной от фазы реализации — даже если это всего 30-минутный блок. Тесты, написанные параллельно с кодом, склонны зеркалить код; тесты, написанные до — заставляют думать с *позиции потребителя*, что порождает лучшие API и ловит больше багов.
