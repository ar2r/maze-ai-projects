# Maze Runner

Клиентская браузерная игра-лабиринт на TypeScript, Vite и Canvas. Проходите через процедурно сгенерированные лабиринты, которые становятся сложнее с каждым уровнем. Работает на ПК (мышь/клавиатура) и мобильных устройствах (тач/виртуальный джойстик).

## Возможности

- **Процедурная генерация лабиринтов** — алгоритм DFS Backtracker с детерминированным ГПСЧ (mulberry32), обеспечивает воспроизводимые лабиринты по сиду
- **Прогрессивная сложность** — с каждым уровнем сетка растёт, клетки уменьшаются, появляются ложные развилки
- **Несколько способов управления** — WASD/стрелки, следование за мышью (шарик движется к курсору), виртуальный джойстик на тач-экранах
- **Пиксельный ретро-стиль** — тёмно-синий фон, неоновые стены, светящийся игрок и маркер выхода
- **Плавная камера** — камера с интерполяцией (lerp): центрирует маленькие лабиринты и следит за игроком на больших
- **Коллизии со скольжением** — разрешение столкновений «круг vs отрезок», игрок плавно скользит вдоль стен
- **Чиптюн-звук** — синтез звуков через Web Audio API (прямоугольные волны): удар о стену, победа, клик
- **Сохранение прогресса** — localStorage хранит текущий уровень, лучшее время по уровням и настройки
- **Пауза/Продолжение** — клавиша Escape или кнопка паузы
- **Обучение** — при первом запуске показывается туториал с описанием управления
- **Вибрация** — тактильная обратная связь при ударе о стену (на поддерживаемых устройствах)
- **Поддержка HiDPI** — Canvas масштабируется по devicePixelRatio для чёткого рендеринга
- **Отладочный оверлей** — переключаемое отображение FPS, сида, размера сетки и позиции игрока
- **Оптимизация под мобильные** — блокировка скролла/зума, полноэкранный Canvas

## Быстрый старт

### Требования

- Node.js 18+
- npm

### Установка и запуск

```bash
# Установка зависимостей
npm install

# Запуск dev-сервера (горячая перезагрузка)
npm run dev

# Запуск тестов
npm test

# Тесты в режиме наблюдения
npm run test:watch

# Продакшн-сборка
npm run build

# Предпросмотр продакшн-сборки
npm run preview
```

Dev-сервер запускается по адресу `http://localhost:5173`.

## Управление

| Ввод | Действие |
|---|---|
| WASD / Стрелки | Движение игрока |
| Мышь (движение курсора) | Игрок следует в направлении курсора |
| Тач (перетаскивание) | Появляется виртуальный джойстик |
| Escape / кнопка паузы | Пауза / Продолжение |
| Иконка шестерёнки | Настройки (звук, вибрация, отладка) |

Клавиатура имеет приоритет над указателем, когда оба активны.

## Как это работает

1. **Генерация лабиринта**: DFS Backtracker создаёт «совершенный» лабиринт (единственный путь между любыми двумя клетками), затем удаляются дополнительные стены для создания ложных развилок. Старт и выход размещаются в двух наиболее удалённых клетках (определяются двойным BFS).
2. **Масштабирование сложности**: каждый уровень увеличивает размер сетки, уменьшает размер клеток и добавляет больше ложных развилок.
3. **Коллизии**: из сетки извлекаются отрезки стен. Тест «круг vs отрезок» с проекцией на ближайшую точку разрешает столкновения за 4 итерации для корректной обработки углов.
4. **Рендеринг**: стены лабиринта рисуются один раз во внеэкранный буфер. Каждый кадр перерисовываются только игрок и эффекты — целевые 60 FPS.

## Ретроспектива TDD

Проект разрабатывался по методологии Test-Driven Development. Ниже — честный разбор опыта.

### Что сработало хорошо

- **Генерация лабиринтов — идеальный кандидат для TDD.** Модули ГПСЧ, генератора, решателя и сложности — чистые функции с чёткими входами и выходами. Написание тестов первыми заставило точно специфицировать поведение. Например, определить, что лабиринт 5x5 должен иметь ровно 24 прохода (N-1 для совершенного лабиринта), — до написания кода генерации.
- **Баги в коллизиях были пойманы рано.** Тест «игрок не должен проходить сквозь стену» изначально провалился (red-фаза), что выявило ошибку в самом тесте — игрок был размещён уже за стеной (расстояние > радиуса = нет столкновения). Исправление теста привело к гораздо более чёткому пониманию математики коллизий.
- **Рефакторинг с уверенностью.** После перехода всех тестов в зелёное состояние разрешение коллизий было переработано с 1 итерации до 4 (для обработки углов). Тесты подтвердили, что ничего не сломалось.
- **Детерминированный ГПСЧ сделал тесты стабильными.** Каждый тест лабиринта использует фиксированный сид — результаты воспроизводимы от запуска к запуску. Нестабильных тестов нет.

### Что не сработало

- **Модули, зависящие от DOM, не покрыты юнит-тестами.** Система ввода (клавиатура, указатель, менеджер), рендеринг, аудио-синтезатор и управление экранами зависят от DOM, Canvas API и Web Audio API. Они написаны без тестов. В более крупном проекте это было бы существенным пробелом.
- **TDD замедлил начальную разработку.** Написание тестов для генератора лабиринтов потребовало полной спецификации ожидаемой структуры до написания алгоритма. Это сместило усилия на начальный этап, тогда как обычно процесс был бы итеративным.
- **Пробел в интеграционном тестировании.** Все 63 теста проверяют отдельные модули, но ни один автоматический тест не проверяет работу полного игрового цикла. Оркестратор (`main.ts`) связывает ~15 модулей, и потенциальные проблемы интеграции юнит-тесты не ловят.

### Плюсы TDD для данного проекта

1. Чисто алгоритмические модули (ГПСЧ, генерация, решатель, коллизии) получили огромную выгоду — TDD идеален для кода с чёткими математическими контрактами.
2. Тесты работают как живая документация: чтение `generator.test.ts` объясняет, что именно гарантирует генератор.
3. Баги в настройке тестов (как с тестом прохождения сквозь стену) выявили недопонимание на ранней стадии, а не в рантайме.
4. Набор из 63 тестов выполняется менее чем за 200 мс — мгновенная обратная связь при разработке.

### Минусы TDD для данного проекта

1. ~40% кодовой базы (рендеринг, ввод, аудио, UI) невозможно осмысленно покрыть TDD без тяжёлого мокинга или браузерного тест-раннера (Playwright и т.д.).
2. Написание тестов для очевидного кода (например, «clamp возвращает min, когда значение < min») добавило накладные расходы с минимальной ценностью для предотвращения багов.
3. Строгий цикл red-green-refactor местами ощущался вынужденным для экспериментального кода вроде аудио-синтезатора, где «спецификация» субъективна (хорошо ли звучит?).

### Как улучшить в следующий раз

- Использовать **Playwright или Cypress** для интеграционных/E2E-тестов, чтобы покрыть оставшиеся 40%, зависящие от DOM.
- Применять TDD строго только к **алгоритмическим/логическим модулям**; для UI/рендеринга использовать более лёгкий подход (написать код, затем добавить регрессионные тесты).
- Добавить **CI-пайплайн**, запускающий юнит-тесты и headless-браузерный smoke-тест при каждом коммите.
- Рассмотреть **property-based тестирование** (например, fast-check) для генерации лабиринтов — проверять инварианты вроде «каждая клетка достижима» на тысячах случайных сидов вместо проверки конкретных.

## Технологический стек

- **TypeScript** — типобезопасность по всей кодовой базе
- **Vite** — быстрый dev-сервер и оптимизированная продакшн-сборка
- **Vitest** — тест-раннер, совместимый с трансформ-пайплайном Vite
- **Canvas API** — весь рендеринг (без DOM-элементов для игровой графики)
- **Web Audio API** — синтез чиптюн-звуков (без аудиофайлов)
